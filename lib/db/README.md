# Backend drivers

ORBIT ships with **two interchangeable backends** behind one data-access contract:

| Mode | When | Storage | Auth |
|---|---|---|---|
| **Local (default)** | No Supabase env vars set | SQLite at `.orbit-local/orbit.db` (better-sqlite3) | Email/password, scrypt hashes, signed HTTP-only session cookies |
| **Supabase (production)** | `NEXT_PUBLIC_SUPABASE_URL` + anon key set | Supabase Postgres (migrations in `supabase/migrations/`) | Supabase Auth |

## The contract

Pages never touch a database client directly. Everything goes through `lib/data/*`
(search, monitors, collections, activity, analytics, misc), which currently
implements the local SQLite driver. The shapes in `lib/types.ts` are the stable
contract: a Supabase implementation of the same functions returns identical
types, so no page changes when the driver swaps (plan §6/§8).

```
app pages → lib/data/* → lib/db/* (SQLite, today)
                    ↘ (future) lib/supabase/* (Postgres)
```

## Local mode notes

- The SQLite database is created and seeded on first request (48 sample
  opportunities, plans, video reviews). Delete `.orbit-local/` to reset.
- Every new signup is seeded with per-user demo content (6 monitors, 15
  notifications, 20 activity events, 4 collections) so all pages have content
  on first login.
- `lib/auth/password.ts` (node:crypto) is server-only; `lib/auth/session.ts`
  uses Web Crypto only, which is why middleware can verify sessions at the
  edge without touching the database.
- Set `ORBIT_SESSION_SECRET` in any shared deployment — see `.env.local.example`.

## Supabase path

1. Create a Supabase project and run the migrations:
   `supabase/migrations/0001_schema.sql` (schema, RLS, profile trigger),
   `supabase/migrations/0002_seed.sql` (plans + global sample content,
   generated by `npx tsx scripts/generate-supabase-seed.ts`).
2. Set the env vars from `.env.local.example`.
3. Implement `lib/data/*` against `getSupabaseServerClient()` (this repo ships
   the client helpers in `lib/supabase/`); RLS policies in the migration
   already scope every table to `auth.uid()`.

Per-user demo content on first login is intentionally app-side (idempotent on
`profiles.onboarded_at`) so it works identically in both modes.
