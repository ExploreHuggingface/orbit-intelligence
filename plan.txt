## How to Read This Document

This is not a feature list. It is a **complete build specification** organized in the order you will execute it: first the product thesis, then the system architecture, then the data pipeline, then the design system, then every page with its exact behavior, then the implementation sequence. Every section is written to be handed to a coding agent or a development team without further clarification.

The frontend prototype and the production backend are specified together because the frontend must be architected against the backend contract from day one. Building the UI against mock data with a different shape than the real API is the most common cause of expensive rewrites in SaaS products.

# Part I — Product Thesis & Scope

## 1. What ORBIT Is

**ORBIT Intelligence** is a personal internet intelligence platform that continuously searches the web for products, properties, investments, rare items, price drops, and emerging opportunities. Users describe what they want in natural language; ORBIT finds relevant listings across marketplaces, compares prices against estimated reference values, tracks availability, scores each match, and notifies users when new matching results appear.

The product sits at the intersection of three categories that are usually separate:

| Category | What it provides | What it lacks |
|---|---|---|
| **Search engine** | Discovery | No persistence, no monitoring, no evaluation |
| **CRM** | Organization and workflow | No autonomous discovery |
| **Market intelligence** | Analysis | No personal, actionable opportunity tracking |

ORBIT is the **operational layer** that turns passive web search into an active opportunity pipeline. It is a command center, not a chatbot. Every interaction produces a structured record — a monitor, an opportunity, a collection, a comparison, a notification — not a conversation transcript.

## 2. Who Uses It and Why

The primary user is a **high-intent individual operator** — an investor, collector, restorer, or deal-hunter who currently manages discovery across spreadsheets, browser bookmarks, and manual marketplace checks. They are willing to pay $49–$299 per month because a single missed opportunity (a mispriced property, a rare part that sells in hours, a watch listed below market) costs more than a year of subscription.

**Representative workflows:**

A real estate investor wants apartments in Berlin-Friedrichshain under €350k with an estimated gross rental yield above 5.5%. Today they check ImmobilienScout24 and Kleinanzeigen twice a day. ORBIT monitors both sources continuously, scores each new listing against their yield model, and pushes a notification with the deal analysis already computed.

A Porsche restorer needs an OEM 911 (997-generation) headlight. These appear on forums and eBay irregularly and sell within hours. ORBIT watches the relevant sources, matches on part number and condition, and alerts instantly — while the listing is still live.

A watch collector wants an Omega Seamaster below €4,000 in excellent condition with box and papers. ORBIT monitors Chrono24 and eBay, compares each listing to a reference price band, and flags the ones that are meaningfully below it.

## 3. Scope Boundaries

**In scope for the React prototype:** every page, every interaction, every state transition, full LocalStorage persistence, realistic demo data, functional search over the demo dataset, functional monitor CRUD, functional charts with date filters, and a service layer that mirrors the production API contract.

**Out of scope for the prototype (explicitly labeled as not connected):** live web crawling, real-time price verification, actual seller availability checks, genuine AI inference, payment processing, and authentication beyond a mock session.

**The simulation boundary is a design requirement, not an apology.** Every demo record carries an `isSample: true` flag. Every simulated monitor match displays a "Simulated match — backend crawling not connected" badge. The monitor creation flow ends with a toast: "Monitor saved. Background crawling will activate when the backend is connected." No part of the UI claims 24/7 live monitoring.

# Part II — Technical Architecture

## 4. Frontend Stack (Prototype)

Use the existing repository's stack where compatible. The target stack:

| Layer | Technology | Rationale |
|---|---|---|
| Bundler | **Vite 7+** | Fastest cold start and HMR; standard for new React apps |
| Framework | **React 18+** (19 if available) | Concurrent rendering, Suspense |
| Language | **TypeScript 5+ (strict)** | Non-negotiable for a project of this size |
| Routing | **React Router 7** (or TanStack Router if the repo already uses it) | File-based or config-based; must support nested layouts |
| Server state | **TanStack Query 5** | Caching, loading/error states, refetching, optimistic updates — all server data flows through it |
| Client state | **Zustand 5** | Sidebar collapsed, theme, selected filters, UI preferences — *never* server data |
| Forms | **React Hook Form + Zod** | Monitor creation (multi-step), settings, filters |
| UI primitives | **shadcn/ui + Radix** (if not already present) | Accessible, unstyled-then-styled components; no runtime lock-in |
| Styling | **Tailwind CSS 4** | Utility-first with design tokens; v4 is the 2026 standard |
| Icons | **Lucide React** | Consistent stroke system, no emoji |
| Charts | **Recharts** | Responsive, composable, tooltip support |
| Toasts | **Sonner** (or shadcn toast) | Accessible, stacked, dismissible |
| Testing | **Vitest + React Testing Library + MSW** | Unit, component, and API-mock integration tests |

**State management discipline — this is an architectural rule, not a suggestion:**

TanStack Query owns **all data that originates from a server** (in the prototype, from the service layer): opportunities, monitors, notifications, collections, activity, market charts. Zustand owns **only pure client state**: whether the sidebar is collapsed, which filter panel is open, the current view mode (grid/table), the selected comparison IDs. Never cache server data in Zustand. Never put UI preferences in TanStack Query.

## 5. Service Layer — The Backend Contract

The frontend never imports `demoData.ts` directly in a component. Every data access goes through a service module. In the prototype these modules return demo data and persist to LocalStorage; in production they call the backend API. **The method signatures do not change between the two implementations.**

```
src/services/
  searchService.ts       → search(query, filters, page), getSuggestions(query), getRecentQueries()
  opportunityService.ts  → list(filters), getById(id), updateStatus(id, status), bulkUpdate(ids, status)
  monitorService.ts      → list(), getById(id), create(payload), update(id, payload), pause(id), resume(id), delete(id), runSimulated(id)
  collectionService.ts   → list(), create(name), addItem(collectionId, opportunityId), removeItem(collectionId, opportunityId)
  notificationService.ts → list(), markRead(id), markAllRead(), getUnreadCount()
  activityService.ts     → list(filters), log(event)
  analyticsService.ts    → getDiscoveries(range), getPriceDropsByCategory(range), getDealScoreDistribution(range), getMarketVsListing(range)
```

Each service returns a `Promise` with a realistic latency (150–400ms simulated) so that loading and error states are actually exercised during development. Each service also exposes an `isSimulated: true` flag on every record, which the UI uses to render the sample-data badge.

**Production backend target** (not built in this prototype, but the contract is designed for it): a Node.js (TypeScript) API or a Python FastAPI service, backed by PostgreSQL for relational data (users, monitors, opportunities, collections), a vector database for semantic search (see Section 7), and a job queue (BullMQ or Celery) for scheduled crawl jobs.

## 6. Web Crawling Architecture (Production Reference)

The prototype does not crawl. The production system uses a **tiered crawling strategy** because no single scraper wins on every source type.

### 6.1 The Three Tiers

| Tier | Tool | What it handles | Why not a single tool |
|---|---|---|---|
| **Tier 1 — General web intelligence** | **Firecrawl** (hosted API or self-hosted AGPL) | Natural-language discovery queries across arbitrary sites. Returns LLM-ready Markdown or structured JSON via `/scrape`, `/crawl`, `/map`, `/search`, and `/extract`. The `/extract` endpoint accepts natural-language schemas — no CSS selectors. Handles JS rendering, proxy rotation, and anti-bot mitigation automatically. | Best for breadth and LLM-readiness; not optimized for high-frequency polling of a known marketplace endpoint. |
| **Tier 2 — Marketplace-specific** | **Apify Actors** | Pre-built scrapers for Amazon, eBay, Zillow, ImmobilienScout24, Chrono24, Kleinanzeigen, and thousands more. Run an actor via REST, receive normalized JSON. | Actor quality varies by marketplace; not every niche forum has an actor. |
| **Tier 3 — Custom JS-heavy / anti-bot** | **Playwright + Crawlee** (Node/TypeScript) | Real estate portals that re-fetch results via map-bounds XHR, hide price data in JSON-LD, or sit behind Cloudflare/AWS WAF. Crawlee provides request queues, proxy rotation, auto-scaling, and Playwright/Puppeteer crawler wrappers. | Highest control, highest operational cost; used only where Tiers 1–2 fail. |

### 6.2 Data Pipeline — From Crawl to Opportunity

The pipeline is an **indexing pipeline** and a **query pipeline**, mirroring the architecture used in production AI search systems.

**Indexing pipeline (runs on a schedule per monitor):**

```
Monitor criteria → Crawl job enqueued → Source fetched (Firecrawl / Apify / Playwright)
→ Raw HTML or JSON → Normalization to common Opportunity schema
→ LLM entity extraction (title, price, currency, location, attributes, condition, seller)
→ Embedding generation → Vector database upsert
→ Match scoring against monitor criteria → Ranked opportunity records
→ Notification event emitted if score exceeds threshold
```

Entity extraction uses **schema-constrained LLM extraction with gleaning** — a two-pass approach that catches 20–30% additional entities by re-asking the model what it missed on the first pass. Extracted values are normalized through a multi-step process: backfill missing fields, ground values against the source text, deduplicate same-name entities with different labels, and validate against a category taxonomy.

**Query pipeline (when a user searches or a monitor is evaluated):**

```
User query → Embedding → Vector similarity search (hybrid: vector + keyword)
→ Retrieve top-K candidates → Rerank against the structured query intent
→ Apply hard filters (price range, category, location)
→ Score and rank → Return paginated results
```

The two-stage retrieval (vector search → rerank) is not optional. Vector proximity is a proxy for semantic similarity, not for whether a document answers the query. A reranking model asks "Does this listing match the user's actual criteria?" rather than "Is this listing about similar things?".

### 6.3 Vector Database Selection

| Option | Strengths | When to choose |
|---|---|---|
| **Qdrant** | Named vectors, hybrid search, multi-stage queries, weighted reranking, on-prem, quantization, on-disk storage | Default choice for self-hosted production with hybrid search needs |
| **Milvus** | Distributed, massive multi-tenancy, independent scaling of ingestion/indexing/query | When write throughput and tenant isolation dominate |
| **pgvector** | Lives in PostgreSQL, no separate infrastructure, `unnest` batch inserts | Early stage or when the relational database already exists |
| **Elasticsearch Vector Database** | Serverless, built-in hybrid search, managed embeddings via Jina models, binary quantization (32× memory reduction) | When operational simplicity and predictable cost matter more than full control |

**Recommendation for ORBIT:** start with **pgvector** in the prototype-to-production transition (no new infrastructure), migrate to **Qdrant** when hybrid search and reranking latency become the bottleneck, and consider **Elasticsearch Vector Database** if the team prefers a managed, serverless path.

## 7. Data Model

Every record in the system conforms to one of these types. The same TypeScript types are used by the service layer and the UI.

```typescript
type OpportunityCategory =
  | "real_estate" | "cars_parts" | "watches"
  | "electronics" | "home_living" | "fashion" | "other";

type OpportunityStatus =
  | "new" | "shortlisted" | "under_review"
  | "dismissed" | "purchased" | "completed";

interface Opportunity {
  id: string;
  title: string;
  description: string;
  category: OpportunityCategory;
  imageUrl: string | null;          // fallback placeholder if null
  sourceMarketplace: string;
  sourceUrl: string;
  currentPrice: number;
  currency: string;
  previousPrice: number | null;
  estimatedMarketValue: number | null;   // labeled "illustrative estimate"
  priceChangePct: number | null;
  dealScore: number;                     // 0–100
  matchScore: number;                    // 0–100 against originating monitor
  status: OpportunityStatus;
  discoveredAt: string;                  // ISO 8601
  lastCheckedAt: string | null;
  isSample: true;                        // prototype records
  evidenceLinks: string[];
  attributes: Record<string, string | number | boolean>;
  realEstate?: {
    city: string;
    neighborhood: string;
    areaSqm: number;
    bedrooms: number;
    askingPrice: number;
    estimatedMonthlyRent: number;
    grossYieldPct: number;
    estimatedAnnualExpenses: number;
    netYieldPct: number | null;
  };
  priceHistory: { date: string; price: number }[];
}
```

Monitors, collections, notifications, and activity events follow the same pattern: a typed record with an `isSample` flag, a stable ID, and ISO timestamps. See the folder structure in Part VIII for file locations.

# Part III — Design System

## 8. Visual Language

The interface must feel like **precision-engineered enterprise software with editorial restraint** — the quality bar set by Attio, Linear, and Stripe, but with its own identity.

Attio's design system demonstrates the principle clearly: a near-white canvas, near-black type, one vivid accent color, and micro-detail rather than decoration. Headlines carry significant negative letter-spacing; body text uses weight 500 (heavier than typical) for readability in dense UIs; the palette is deliberately achromatic except for state communication. Linear achieves a similar effect with Inter Variable, OpenType stylistic sets, and consistent 400–590 weight discipline. Stripe uses a single typeface at weight 300 across all sizes, reading as "confident restraint rather than corporate shouting".

ORBIT adopts these principles: **one accent color used sparingly, typographic hierarchy through weight and tracking rather than size alone, and borders/shadows that recede rather than announce.**

### 8.1 Color Tokens

All colors are semantic tokens. No component hardcodes a hex value. Use CSS custom properties (`--color-*`) so the system can be themed later.

| Token | Value | Role |
|---|---|---|
| `--color-canvas` | `#F7F8FA` | Page background |
| `--color-surface` | `#FFFFFF` | Cards, sidebar, topbar |
| `--color-surface-subtle` | `#FCFCFD` | Nested surfaces, table header |
| `--color-ink` | `#172033` | Primary text |
| `--color-ink-secondary` | `#667085` | Secondary text, descriptions |
| `--color-ink-tertiary` | `#98A2B3` | Captions, placeholders |
| `--color-accent` | `#635BFF` | Primary actions, active nav, focus rings |
| `--color-accent-subtle` | `#F0EFFF` | Active nav background, accent wash |
| `--color-border` | `#E7EAF0` | Card borders, dividers, input borders |
| `--color-border-strong` | `#D0D5DD` | Emphasized borders, hover state |
| `--color-success` | `#16A36A` | Positive trends, deal wins |
| `--color-warning` | `#E6A23C` | Caution badges, expiring monitors |
| `--color-danger` | `#E05260` | Destructive actions, price increases |
| `--color-info` | `#667085` | Neutral badges |

### 8.2 Typography

**Typeface:** Inter Variable (or `Inter` with fallback to system sans). Enable OpenType feature `"ss03"` globally for character disambiguation in data-dense tables.

| Role | Size | Weight | Tracking | Line height |
|---|---|---|---|---|
| Display / H1 | 28px | 600 | -0.02em | 1.2 |
| H2 / Section | 20px | 600 | -0.015em | 1.3 |
| H3 / Card title | 15px | 600 | -0.01em | 1.4 |
| Body | 14px | 500 | -0.006em | 1.5 |
| Small / Table cell | 13px | 500 | 0 | 1.45 |
| Caption / Label | 12px | 500 | 0.01em | 1.4 |
| Mono / Price | 13px | 500 | 0 | tabular-nums |

Use `font-variant-numeric: tabular-nums` on all price, score, and metric displays. Prices should never shift horizontally as values change.

### 8.3 Spacing & Layout

A 4px base unit. Component padding: 12px (compact), 16px (default), 20px (comfortable), 24px (section). Card radius: 12px. Button radius: 8px (not pill-shaped — excessive rounding is a design smell). Input radius: 8px. Border width: 1px throughout; shadows are soft and blue-tinted at very low opacity (max `0 1px 3px rgba(23, 32, 51, 0.04)`).

**Layout structure:** persistent left sidebar (240px expanded, 64px collapsed), slim topbar (56px), main content area with `max-width: 1440px` and horizontal padding of 32px (desktop), 24px (tablet), 16px (mobile).

### 8.4 Component States

Every interactive element has defined states for **default, hover, focus-visible, active, disabled, and loading**. Focus rings use `--color-accent` at 2px offset. Buttons show a spinner and disable during async actions. Tables show skeleton rows on initial load; empty states show a lucide icon, a one-line explanation, and a primary action. Error states show a retry button and preserve the user's input.

**No emoji anywhere.** Icons are Lucide, 16px or 18px, stroke width 1.75. Status is communicated through badges (small, 11px uppercase label, semantic background at 10% opacity) — not through colored dots alone.

**Step 1 — Define what to monitor:** natural language description textarea (required, min 10 chars), category select, optional URL/domain restriction input (e.g., `immobilienscout24.de`). Helper text: "Describe the opportunity in plain language. Include location, condition, or any attributes that matter."

**Step 2 — Matching criteria:** price range (min/max), keywords (tag input), required attributes (key-value pairs or checkboxes depending on category), excluded terms (tag input), match sensitivity slider (Broad / Balanced / Strict). Each sensitivity level shows a one-line explanation.

**Step 3 — Notifications:** toggles for In-app notifications (on by default), Email (off), Instant alerts vs. Daily digest (radio), Price-drop-only alerts (toggle). Disabled states explained: "Email requires account verification — not available in this prototype."

**Step 4 — Review:** monitor name (editable, auto-generated from the description), a read-only summary of all criteria, estimated monitoring frequency ("Every 30 minutes — simulated in this prototype"), and an "Activate Monitor" primary button.

**On submit:** the monitor is saved to LocalStorage, the modal closes, and a toast appears: "Monitor saved. Background crawling will activate when the backend is connected." A simulated match event may fire after 3–5 seconds: a notification appears in the bell dropdown and on the Notifications page, labeled **"Simulated match — demo data"**. This simulates the monitoring loop without claiming live crawling.

**Edit mode:** the same modal opens pre-filled; the submit button reads "Save changes". **Pause/resume** updates the status in the table and persists. **Delete** opens a confirmation dialog with the monitor name, and on confirm removes it and shows a toast with an "Undo" action (undo restores it from a temporary state).

## 15. Collections Page (`/collections`)

Sidebar list of collections (Dream Home Investments, Watch Wishlist, Rare Car Parts, Home Upgrade) with item counts. Clicking a collection shows its items in a grid or table. "New Collection" button opens a small inline form (name input + create). Items can be removed from a collection (with undo toast). Adding items happens from the opportunity detail drawer — the collection page shows a "Add items" hint that links to Discover.

**Empty state per collection:** "No items yet. Browse Discover and click 'Save to collection' on any opportunity."

## 16. Comparisons Page (`/comparisons`)

Select 2–4 opportunities via a search-and-select interface or from a collection. The comparison table renders columns for each selected item and rows for: price, estimated market value, condition, key features, seller, source, availability, match score. For real estate, additional rows: area, bedrooms, asking price, estimated monthly rent, gross yield, net yield (if available). Differences are highlighted with a subtle accent wash on the best value per row — **not** with exaggerated badges or "WINNER" labels. A note below the table: "Comparison based on sample data. Estimated values are illustrative."

## 17. Notifications Page (`/notifications`)

Tabs: All, Price Drops, New Matches, Availability Alerts, Monitor Updates. Each notification row: icon by type, title, description, timestamp, read/unread indicator (a small accent dot), and a link to the associated opportunity. Actions: click to mark read and navigate; "Mark all as read" button at the top; unread count persists to LocalStorage.

**Sample notifications:** "Price drop: Omega Seamaster reduced by 8% — now €3,250", "New match: Berlin apartment in Friedrichshain matches 'Berlin apartments under €350k'", "Monitor update: 'Porsche 911 OEM parts' checked 12 sources — 1 new match", "Availability alert: Sony Alpha Camera Bundle back in stock at €1,180".

## 18. Market Insights Page (`/market-insights`)

Category trend cards (average price, 30-day change, listing volume), a large area chart of average prices by category over time, a distribution chart of opportunities by category (donut or horizontal bar), and a "Top movers" table (categories with the largest price drops). Date range selector (30/90/180 days) that updates all charts.

## 19. Price History Page (`/price-history`)

A searchable list of tracked items with sparklines. Selecting an item shows a full-width price history chart with annotations for price drops, plus a listing timeline table (date, event, price, source). Data comes from `priceHistory` arrays in `demoData`.

## 20. Video Reviews Page (`/video-reviews`)

Grid of video review cards: thumbnail (placeholder gradient with play icon if no image), title, reviewer/source, duration, associated product (linked to the opportunity), and a source link. Filter by category and search by title. Clearly labeled "Curated sample content — external links are illustrative."

## 21. Activity Page (`/activity`)

Chronological feed of all user actions and simulated monitoring events: searches run, monitors created/edited/paused, opportunities shortlisted/dismissed, collections updated, notifications read. Searchable by text and filterable by event type. Each event has a timestamp and a link to the relevant record.

## 22. Integrations Page (`/integrations`)

Cards for supported marketplaces: Amazon, eBay, Zillow, ImmobilienScout24, Chrono24, Kleinanzeigen, Bring a Trailer, eBay Kleinanzeigen. Each card shows the marketplace logo (or a text mark), a one-line description, and a status badge: **"Not yet connected"** (for all of them in the prototype) with a "Request integration" button that opens a modal explaining that integrations require the production backend. A second section lists "Potential integrations" (Slack, Notion, Google Sheets, Zapier) with the same not-connected treatment. **No card should imply that a live connection exists.**

## 23. Settings Page (`/settings`)

Tabs: Profile, Workspace, Notifications, Data, Account.

- **Profile:** name, email (mock), avatar placeholder, timezone select. Save persists to LocalStorage and shows a toast.
- **Workspace:** default category, default currency, items per page, theme (Light only — Dark shown as disabled with "Coming later").
- **Notifications:** toggles for in-app, email (disabled with explanation), weekly digest, price-drop alerts. Saved state persists.
- **Data:** "Export demo data" (downloads a JSON of the current LocalStorage state), "Reset demo data" (confirmation dialog, restores the seed data), "Clear all collections" (confirmation).
- **Account:** plan indicator (Pro, $99/mo — sample), usage ("12 of 20 monitors used"), "Manage plan" button (opens a modal explaining billing is not connected in the prototype), sign-out (clears mock session and redirects to a lightweight mock sign-in screen).

# Part VI — Interaction & State Requirements

## 24. Every Element Must Work

This is a quality gate, not a suggestion. The following must have meaningful behavior:

Sidebar navigation (React Router), search submission, category chips, example queries, KPI card clicks, table sorting, search-within-results, pagination/load-more, row click → detail drawer, star/watchlist toggle, monitor create/edit/pause/resume/delete, monitor form step navigation with validation, notification read/unread and mark-all, collection create/add/remove, comparison select and remove, date-range filters on charts, settings form save, export/reset data, toast on every mutating action, empty/loading/error states, keyboard focus rings, aria labels on icon-only buttons, and LocalStorage persistence across all user-created records.

**Forbidden:** `<a href="#">`, buttons with empty `onClick`, disabled buttons without an explanation, and search buttons that do nothing.

## 25. State Persistence Map

| Key | Contents | Written by |
|---|---|---|
| `orbit.monitors` | User-created and edited monitors | Monitor service |
| `orbit.opportunities` | Status changes, watchlist flags | Opportunity service |
| `orbit.collections` | Collections and their item IDs | Collection service |
| `orbit.notifications` | Read/unread state | Notification service |
| `orbit.activity` | Append-only activity log | Activity service |
| `orbit.recentQueries` | Last 10 search queries | Search service |
| `orbit.ui` | Sidebar collapsed, view mode | Zustand persist |
| `orbit.settings` | User preferences | Settings form |

On first load, if a key is absent, seed from `demoData`. On reset, clear the keys and re-seed. The export function serializes all keys.

## 26. Loading, Empty, and Error States

**Loading:** skeleton rows in tables (3–5 rows), skeleton cards in grids, a spinner inside primary buttons during async actions. Simulated latency of 150–400ms ensures these states are visible.

**Empty:** contextual icon, one-sentence explanation, and a primary action. Examples: "No monitors yet. Create your first monitor to start tracking opportunities." / "No results for 'xyz'. Try a broader query or different filters." / "No notifications. You're all caught up."

**Error:** a card with a retry button, preserving the user's input and filters. Errors can be simulated in development via a query param (`?simulateError=true`) to verify the state.

# Part IX — Production Path (Beyond the Prototype)

The prototype is designed so that the following production work requires no page-level rewrites — only service-layer implementation swaps.

**Backend:** Node.js (TypeScript) API or Python FastAPI. PostgreSQL for relational data. A vector database (pgvector → Qdrant as scale demands) for semantic search. A job queue (BullMQ or Celery) with a scheduler for monitor crawl frequency. WebSocket or Server-Sent Events for real-time notification push.

**Crawling:** the three-tier strategy in Section 6 — Firecrawl for general discovery, Apify Actors for marketplace-specific extraction, Playwright + Crawlee for anti-bot-heavy sources. Results normalized into the `Opportunity` schema, embedded, and upserted.

**AI layer:** embedding model for semantic search (Cohere Embed, Voyage, or OpenAI `text-embedding-3`), a reranking model for precision (Cohere Rerank or a cross-encoder), and an LLM for schema-constrained entity extraction with gleaning. The match scoring service combines attribute match, price deviation, and freshness into the `dealScore`.

**Authentication:** replace the mock session with a real auth provider (Clerk, Auth0, or Supabase Auth). The prototype's user avatar and settings pages already have the correct shape for a real user object.

**Billing:** Stripe for subscriptions. The plan indicator and usage meter in the sidebar already read from a `plan` object — swap the mock for the Stripe customer portal.

**The service contract does not change.** `searchService.search()` returns a `Promise<SearchResult>` in the prototype (from `demoData`) and in production (from the API). The UI layer is identical.
